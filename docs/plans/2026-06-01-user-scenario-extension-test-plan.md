# FDS Inspector 사용자 작업 시나리오 테스트 계획서

검수 기준일: 2026-06-01

## 목적

FDS Inspector를 실제 사용자가 업무 페이지에서 쓰는 흐름 기준으로 검수한다. 목표는 단순히 위반을 찾는 것이 아니라, 사용자가 위반 의미, 위치, 영향 범위, 다음 행동을 빠르게 이해하고 실제 수정 작업으로 이어갈 수 있는지 확인하는 것이다. 모든 테스트는 "이 기능이 사용자의 디자인 시스템 검수 시간을 줄이고, 잘못된 판단을 줄이며, 수정 가능한 정보로 이어지는가"를 함께 판정한다.

## 익스텐션의 필요성

서비스 화면의 디자인 시스템 위반은 코드 리뷰나 눈검수만으로 안정적으로 찾기 어렵다. 실제 브라우저에서 계산된 CSS, 동적으로 렌더링된 DOM, 로그인 후에만 보이는 업무 데이터, 반복 컴포넌트의 누적 위반은 Figma 화면이나 정적 코드만 봐서는 놓치기 쉽다.

FDS Inspector는 이 간극을 줄이기 위해 필요하다.

- 실제 Chrome 페이지 위에서 계산된 스타일을 검사한다.
- 토큰 기준과 실제 사용 값을 비교해 디자인 시스템 이탈을 드러낸다.
- 반복되는 위반을 그룹화해 가장 큰 영향부터 보게 한다.
- 결과 목록에서 실제 DOM 요소로 바로 이동시켜 원인 위치를 확인하게 한다.
- 대체 토큰 후보와 복사 액션을 제공해 검수에서 수정 작업으로 이어지게 한다.
- 큰 페이지와 오류 상황에서도 사용자가 검사 신뢰도를 판단할 수 있게 한다.

## 사용자에게 주는 도움

### 디자이너에게 주는 도움

- 실제 구현 화면이 Figma/FDS 기준과 얼마나 어긋나는지 빠르게 확인한다.
- 컬러, 간격, 라운드처럼 시각 품질에 직접 영향을 주는 위반을 값 단위로 확인한다.
- 반복 위반의 영향 범위를 보고 수정 요청 우선순위를 정한다.
- 개발자에게 "어느 값이 어디에서 잘못됐는지" 구체적으로 전달할 수 있다.

### 프론트엔드 엔지니어에게 주는 도움

- 원시값 직접 사용, 미등록 색상, 비규격 spacing/radius를 실제 DOM 요소 기준으로 찾는다.
- 결과 클릭으로 해당 요소 위치를 확인해 CSS 수정 범위를 좁힌다.
- 추천 토큰을 복사해 코드 수정에 바로 사용할 수 있다.
- 대형 페이지에서도 브라우저를 멈추지 않고 반복 위반을 우선순위화한다.

### QA/릴리즈 담당자에게 주는 도움

- 배포 전 디자인 시스템 준수 여부를 반복 가능한 기준으로 확인한다.
- 오류, 빈 결과, 일부 검사 상태를 구분해 검사 결과를 과신하지 않게 한다.
- 동일 fixture와 실제 업무 페이지를 함께 검수해 회귀를 줄인다.

## 가치 기반 검수 원칙

- 발견 가능성: 사용자가 위반이 있다는 사실을 놓치지 않는가.
- 이해 가능성: 사용자가 위반 종류, 값, 영향 범위를 오해하지 않는가.
- 행동 가능성: 사용자가 다음에 무엇을 수정해야 하는지 알 수 있는가.
- 위치 신뢰도: 목록의 항목과 실제 화면 요소가 정확히 연결되는가.
- 작업 지속성: 큰 DOM, 작은 화면, hover/focus, 오류 상태에서도 검수 흐름이 끊기지 않는가.
- 기준 신뢰도: 토큰 기준, 일부 검사, 오류 상태처럼 결과 신뢰도에 영향을 주는 정보를 과하거나 부족하지 않게 전달하는가.
- 인터랙션 피드백: 패널 열림, 탭 전환, 그룹 펼침, 요소 핀, 토큰 복사 같은 상태 변화가 사용자의 다음 행동을 더 분명하게 만드는가.
- 모션 접근성: GSAP 모션이 장식이 아니라 상태 이해를 돕고, `prefers-reduced-motion` 환경에서는 움직임을 줄이는가.

## 검수 범위

### 대상 사용자

- 디자인 시스템 기준을 확인하는 디자이너
- 실제 DOM/CSS 구현을 수정해야 하는 프론트엔드 엔지니어
- 배포 전 페이지 품질을 점검하는 QA 또는 퍼블리셔

### 대상 화면

- 로컬 fixture 3종
  - `http://127.0.0.1:8765/docs/verification/spacing-direction-fixture.html`
  - `http://127.0.0.1:8765/docs/verification/large-dom-scan-fixture.html`
  - `http://127.0.0.1:8765/docs/verification/scan-error-state-fixture.html`
- 실제 업무 페이지
  - LUKE 또는 로그인 후 접근 가능한 실제 서비스 페이지
  - DOM 수가 많고 반복 컴포넌트가 있는 목록/대시보드 페이지
  - 모달, 드롭다운, 스크롤 컨테이너가 있는 인터랙션 페이지

### 검수 축

- 기능: 스캔, 필터 전환, 그룹/상세 클릭, 스크롤 이동, 복사, 재검사
- UX 이해도: 현재 상태, 위반 의미, 영향 범위, 다음 행동
- UI 안정성: 텍스트 잘림, 패널 위치, 작은 화면, 큰 숫자, hover/focus 상태
- 모션/인터랙션: GSAP 기반 패널 등장, 목록 전환, 인스펙터 카드, 핀, 복사 성공 피드백
- 접근성: 키보드 포커스, `aria-label`, 버튼 역할, 시각적 포커스
- 성능: 대형 DOM, 배치 처리, 중복 집계, 응답성
- 오류/복구: 스캔 실패, 토큰 없음, 권한/연결 상태, stale UI 제거

### 세밀 UX 검수 항목

- 툴바 badge: 툴바에서는 기존처럼 숫자를 직접 표시하고, 전체 의미는 접근성 label로 제공한다.
- 상세 패널 탭 이동: BG/Border/Text 또는 상태 카드 전환 시 GSAP 모션이 적용되어 결과 맥락이 바뀐 것을 인지할 수 있다.
- hover 인스펙터 카드: 목록에서 카드로 이동하는 동안 카드가 닫히지 않고, 카드 자체가 pointer interaction을 받아 복사 버튼을 누를 수 있다.
- 긴 텍스트: 목록은 밀도를 위해 핵심 필드를 한 줄로 유지하되, 전체 의미는 `title`/`aria-label`에 보존한다. 인스펙터 카드의 대체 토큰 후보는 줄바꿈으로 실제 내용을 확인할 수 있어야 한다.
- 복사 피드백: 토큰 복사 후 `복사됨` 문구와 짧은 모션이 모두 제공된다.
- 기능 목적성: 새 기능은 "위반 발견 → 실제 위치 확인 → 대체 토큰 확보 → 수정/전달" 흐름을 짧게 만드는 경우에 우선한다.

## 사용자 작업 시나리오

### S01. 처음 켜서 현재 상태를 이해한다

사용자 목표: 확장을 켰을 때 지금 검사 중인지, 검사 결과를 볼 수 있는지, 어떤 카테고리를 선택해야 하는지 이해한다.

검증할 사용자 도움: 사용자가 검사를 시작하자마자 "지금 도구가 정상 동작 중인지"를 판단하고 다음 검사 카테고리로 이동할 수 있어야 한다.

검수 페이지: 모든 fixture, 실제 업무 페이지

절차:

1. 페이지를 연다.
2. 확장 아이콘으로 FDS Inspector를 켠다.
3. 초기 검사 중 상태를 관찰한다.
4. 검사 완료 후 툴바와 상세 패널의 첫 화면을 확인한다.

통과 기준:

- 검사 중에는 로딩/계산 중 상태가 명확하다.
- 완료 후 불필요한 완료 메타가 상세 패널을 밀어내지 않는다.
- 사용자가 컬러, 폰트, 간격, 라운드 중 어떤 검사를 눌러야 하는지 알 수 있다.
- 툴바 badge 숫자 또는 표시가 버튼 안에서 잘리지 않는다.
- 패널이 화면 밖으로 나가거나 페이지 핵심 UI를 완전히 가리지 않는다.

실패 예:

- 검사 완료 후에도 로딩 문구가 남아 있다.
- 숫자가 badge 밖으로 삐져나오거나 버튼 레이아웃을 깨뜨린다.
- 초기 결과가 비어 보이는데 실제로는 다른 tone에 위반이 있다.

### S02. 컬러 위반을 확인하고 우선순위를 판단한다

사용자 목표: 미등록 색상과 원시값 직접 사용을 구분하고, 어떤 색상 패턴부터 수정해야 할지 판단한다.

검증할 사용자 도움: 사용자가 색상 위반을 단순 숫자가 아니라 수정 우선순위와 토큰 대체 필요성으로 이해할 수 있어야 한다.

검수 페이지: Large DOM fixture, 실제 업무 페이지

절차:

1. 컬러 검사를 선택한다.
2. BG, Border, Text 탭을 각각 전환한다.
3. `미등록`, `원시값` 카드와 목록을 비교한다.
4. 첫 번째 그룹을 펼친다.

통과 기준:

- 컬러 검사에서만 BG/Border/Text 탭이 보인다.
- 탭 라벨에는 큰 숫자가 직접 표시되지 않고, 전체 의미는 `aria-label` 또는 tooltip 수준에서 확인 가능하다.
- `미등록`과 `원시값`은 결과가 있는 tone이 우선적으로 보인다.
- 큰 숫자보다 패턴 수와 다음 행동이 먼저 보인다.
- 목록에는 위반 종류, 상태, 값, 영향 요소 수가 한눈에 보인다.
- 사용자는 `#3182f6`, `#f6f8fa` 같은 원시값을 보고 토큰 대체가 필요하다는 결론을 낼 수 있다.

실패 예:

- `0`건인 카드가 선택되어 목록이 빈 상태처럼 보인다.
- Text 탭의 `2,001` 같은 숫자가 탭 UI를 깨뜨린다.
- 목록이 값만 보여주고 `원시값 직접 사용`인지 `미등록`인지 알 수 없다.

### S03. 간격 위반의 방향과 범위를 구분한다

사용자 목표: 전체 패딩, 방향 패딩, 마진 위반을 혼동하지 않고 실제 수정 위치를 찾는다.

검증할 사용자 도움: 사용자가 spacing 위반을 "어느 방향의 어떤 CSS 속성을 고쳐야 하는지"까지 좁힐 수 있어야 한다.

검수 페이지: Spacing Direction fixture, 실제 업무 페이지

절차:

1. 간격 검사를 선택한다.
2. 요약 카드에서 검토 패턴 수와 영향 요소 수를 확인한다.
3. `패딩 14px`, `오른쪽 패딩 14px`, `마진 14px` 그룹을 확인한다.
4. 각 그룹을 클릭해 대표 요소로 이동한다.
5. 펼쳐진 상세 항목 중 하나를 클릭한다.

통과 기준:

- 네 방향이 같은 패딩은 `패딩 14px`으로 표시된다.
- 한 방향만 다른 경우 `오른쪽 패딩 14px`처럼 방향이 표시된다.
- 마진은 패딩과 분리된다.
- 그룹 개수는 `N개 요소`로 표시되어 DOM 영향 범위를 의미한다.
- 그룹 클릭은 대표 요소로 스크롤하고 핀/하이라이트를 보여준다.
- 상세 항목 클릭은 해당 개별 요소로 이동한다.

실패 예:

- 상단 패딩이 아닌데 `상단 패딩 14px`으로 잘못 표시된다.
- 같은 그룹 클릭 후 위치 이동이 없거나 핀이 보이지 않는다.
- 상세 항목과 대표 그룹의 이동 결과가 구분되지 않는다.

### S04. 위반 목록에서 실제 화면 요소를 찾는다

사용자 목표: 결과 목록에서 위반 항목을 클릭했을 때 실제 화면의 어떤 요소가 문제인지 즉시 확인한다.

검증할 사용자 도움: 사용자가 목록의 추상적인 위반 정보를 실제 화면 요소와 연결해 수정 또는 전달 가능한 근거를 얻어야 한다.

검수 페이지: 모든 정상 fixture, 실제 업무 페이지

절차:

1. 위반이 있는 카테고리를 선택한다.
2. 목록 그룹에 마우스를 올린다.
3. 대표 핀과 인스펙터 카드가 표시되는지 본다.
4. 그룹을 클릭한다.
5. 상세 항목을 클릭한다.
6. 필터를 다른 카테고리로 바꾼다.

통과 기준:

- hover 시 대표 요소 하이라이트와 인스펙터 카드가 표시된다.
- 클릭 시 스크롤 위치가 실제 요소를 볼 수 있는 지점으로 이동한다.
- 이동 후 사용자가 “어떤 요소가 문제인지” 시각적으로 알 수 있다.
- 필터 전환 시 이전 핀, 하이라이트, 카드가 남지 않는다.
- 목록 문구나 `aria-label`은 클릭 결과를 설명한다.

실패 예:

- 클릭했지만 아무 변화가 없다.
- 화면 밖 요소로 이동하거나 패널에 가려서 대상이 보이지 않는다.
- 이전 카테고리의 핀이 계속 남아 현재 결과처럼 보인다.

### S05. 추천 토큰을 확인하고 복사한다

사용자 목표: 원시값 위반에서 대체 토큰 후보를 확인하고 토큰명을 복사해 수정 작업에 사용한다.

검증할 사용자 도움: 사용자가 "문제를 찾는 것"에서 멈추지 않고 대체 토큰을 바로 가져가 수정 행동으로 이어갈 수 있어야 한다.

검수 페이지: Large DOM fixture, 실제 업무 페이지

절차:

1. 컬러 검사에서 원시값 그룹을 찾는다.
2. 그룹 또는 상세 항목에 hover한다.
3. 인스펙터 카드의 `대체 토큰` 영역을 확인한다.
4. 목록에서 카드 방향으로 마우스를 이동한다.
5. `토큰명 복사` 버튼을 클릭한다.
6. 성공 피드백을 확인한다.

통과 기준:

- 목록에서 카드로 마우스를 옮겨도 카드가 즉시 닫히지 않는다.
- 카드 안의 복사 버튼에 접근 가능하다.
- 인스펙터 카드의 pointer interaction이 막혀 있지 않다.
- 클릭 후 버튼 문구가 `복사됨`으로 바뀐다.
- 복사 성공 시 짧은 피드백 모션이 있어 클릭이 반영됐음을 알 수 있다.
- 복사할 후보가 여러 개면 전체 후보는 `title`로 확인 가능하고, 기본 복사는 대표 후보를 사용한다.
- 긴 토큰 후보는 카드 안에서 줄바꿈되어 확인 가능하다.
- 복사 실패 시 `복사 실패` 피드백이 표시된다.

실패 예:

- 목록에서 마우스가 벗어나자 카드가 닫혀 버튼을 누를 수 없다.
- 버튼 클릭이 목록 클릭/스크롤 이동으로 오작동한다.
- 어떤 토큰이 복사됐는지 피드백이 없다.

### S06. 빈 결과를 확인하고 다음 행동을 결정한다

사용자 목표: 위반이 없는 카테고리에서 “검사가 안 된 것”인지 “위반이 없는 것”인지 구분한다.

검증할 사용자 도움: 사용자가 빈 결과를 신뢰하고 다음 카테고리 또는 다음 페이지 검수로 넘어갈 수 있어야 한다.

검수 페이지: Spacing Direction fixture의 폰트/라운드 상태, 실제 업무 페이지

절차:

1. 위반이 없을 가능성이 높은 카테고리를 선택한다.
2. 요약 카드와 빈 결과 문구를 확인한다.
3. 다른 카테고리로 전환한 뒤 다시 돌아온다.

통과 기준:

- 빈 결과는 현재 카테고리 기준으로 위반이 없음을 말한다.
- 컬러 전용 탭이 비컬러 검사에 섞이지 않는다.
- 이전 목록이나 이전 핀이 남지 않는다.
- 사용자는 다음 카테고리로 전환해 계속 검수할 수 있다.

실패 예:

- 빈 결과인데 실제로는 다른 tone이나 탭에 위반이 숨어 있다.
- 이전 카테고리 목록이 남아 현재 결과처럼 보인다.
- “결과 없음”만 보이고 어떤 검사의 결과인지 알 수 없다.

### S07. 스캔 오류에서 복구한다

사용자 목표: 오류가 발생했을 때 무엇이 잘못됐고 어떻게 다시 시도할지 이해한다.

검증할 사용자 도움: 사용자가 오류 상태를 정상 결과로 오해하지 않고 재검사 행동을 선택할 수 있어야 한다.

검수 페이지: Error State fixture

절차:

1. 오류 fixture를 연다.
2. 확장을 켜고 컬러 검사를 선택한다.
3. 오류 문구를 확인한다.
4. 새로고침/재검사 버튼을 사용해 복구 가능성을 확인한다.

통과 기준:

- 로딩 문구가 오류 상태와 함께 남지 않는다.
- 오류 문구는 “새로고침 버튼으로 다시 검사”처럼 다음 행동을 포함한다.
- 이전 위반 그룹, 핀, 하이라이트가 남지 않는다.
- 빈 결과 상태와 오류 상태가 서로 모순되어 보이지 않는다.

실패 예:

- 계속 검사 중처럼 보인다.
- 오류가 났는데 위반 목록이 남아 있다.
- 사용자가 재검사해야 하는지 페이지를 새로고침해야 하는지 알 수 없다.

### S08. 큰 페이지에서도 업무를 계속할 수 있다

사용자 목표: DOM이 큰 페이지에서 Chrome이 멈추지 않고, 일부 검사 상태를 신뢰할 수 있게 이해한다.

검증할 사용자 도움: 사용자가 실제 업무 페이지 규모에서도 검수 작업을 중단하지 않고, 검사 범위의 한계를 알고 결과를 해석할 수 있어야 한다.

검수 페이지: Large DOM fixture, 실제 업무 페이지의 목록/대시보드

절차:

1. 대형 DOM 페이지를 연다.
2. 확장을 켠다.
3. 검사 중 페이지 스크롤과 버튼 클릭이 가능한지 확인한다.
4. 검사 완료 후 결과 수와 일부 검사 상태를 확인한다.
5. 카테고리를 빠르게 전환한다.

통과 기준:

- Chrome 응답 없음 모달이 뜨지 않는다.
- 스캔은 배치 처리되어 `batchYieldCount > 0`이다.
- 최대 검사 수를 넘으면 partial/truncated 상태가 기록된다.
- 패널은 큰 숫자보다 패턴과 다음 행동을 먼저 보여준다.
- 카테고리 전환 중 UI가 깨지거나 이전 상태가 섞이지 않는다.

실패 예:

- 스캔 중 브라우저가 멈춘다.
- 6,000개만 검사했는데 전체 페이지를 모두 검사한 것처럼 보인다.
- 결과 수가 너무 커서 탭/카드 레이아웃이 깨진다.

### S09. 작은 화면과 패널 이동을 확인한다

사용자 목표: 작은 뷰포트나 패널 이동 상태에서도 정보가 잘리지 않고 조작 가능하다.

검증할 사용자 도움: 사용자가 브라우저 크기나 패널 위치 때문에 결과를 읽거나 조작하는 일을 포기하지 않아야 한다.

검수 페이지: 모든 fixture

절차:

1. viewport를 390px 너비 근처로 줄인다.
2. 확장을 켠다.
3. 상세 패널을 드래그한다.
4. 각 카테고리 탭과 목록을 확인한다.
5. 닫기 버튼과 툴바 버튼을 조작한다.

통과 기준:

- 툴바와 패널이 viewport 밖으로 나가지 않는다.
- 버튼 텍스트와 badge가 잘리지 않는다.
- 목록 값이 말줄임되더라도 전체 의미는 `title` 또는 접근성 이름에 있다.
- 패널 드래그 후에도 결과 클릭, hover 카드, 복사 버튼이 동작한다.
- 패널 열림/드래그 후 위치 보정이 갑작스럽게 튀어 보이지 않는다.
- 닫기 버튼은 패널만 닫고 툴바 상태를 깨지 않는다.

실패 예:

- 패널이 화면 밖으로 이동해 되돌릴 수 없다.
- 닫기 버튼이나 탭이 가려져 클릭할 수 없다.
- 긴 값 때문에 행 높이나 버튼 크기가 갑자기 깨진다.

### S10. 키보드만으로 주요 검수를 수행한다

사용자 목표: 마우스 없이도 필터 선택, 그룹 확인, 상세 이동, 패널 닫기가 가능하다.

검증할 사용자 도움: 사용자가 입력 방식에 관계없이 주요 검수 흐름을 수행할 수 있어야 한다.

검수 페이지: 모든 fixture

절차:

1. `Tab`으로 툴바 버튼에 이동한다.
2. `Enter` 또는 `Space`로 검사 카테고리를 선택한다.
3. `Tab`으로 요약 카드, 탭, 그룹, 상세 항목을 이동한다.
4. 그룹과 상세 항목에서 `Enter`를 누른다.
5. `Escape` 또는 닫기 버튼으로 패널을 닫는다.

통과 기준:

- 포커스 링이 명확하다.
- 실제 조작 가능한 요소는 `button`이다.
- 그룹 focus 시 대표 요소 미리보기가 표시된다.
- Enter/Space 조작이 마우스 클릭과 같은 결과를 만든다.
- 포커스가 보이지 않거나 페이지 뒤로 사라지지 않는다.
- reduced motion 설정에서도 키보드 조작 흐름은 동일하게 가능하다.

실패 예:

- 포커스 위치를 알 수 없다.
- `div`처럼 보이는 행이 키보드로 조작되지 않는다.
- 키보드 조작 후 스크롤 이동이나 핀이 발생하지 않는다.

### S11. 실제 업무 페이지에서 수정 우선순위를 정한다

사용자 목표: 반복 위반이 많은 실제 페이지에서 가장 큰 영향의 수정부터 정한다.

검증할 사용자 도움: 사용자가 수많은 위반 중 실제 릴리즈 품질에 가장 큰 영향을 주는 수정부터 결정할 수 있어야 한다.

검수 페이지: LUKE 또는 실제 업무 페이지

절차:

1. 실제 페이지를 연다.
2. 컬러, 간격, 라운드 검사를 차례로 선택한다.
3. 각 카테고리에서 가장 영향 요소가 큰 그룹을 찾는다.
4. 해당 그룹을 클릭해 대표 요소를 확인한다.
5. 추천 토큰 또는 위반 값을 기록한다.

통과 기준:

- 반복 위반은 개별 행 수백 개보다 그룹 중심으로 보인다.
- 그룹은 영향 요소 수를 명확히 보여준다.
- 대표 요소가 실제 수정 위치를 추정할 만큼 충분히 보인다.
- 사용자는 “어떤 토큰/값을 어디에 적용해야 하는지”를 말할 수 있다.
- 실제 페이지의 fixed header, modal, scroll container에서도 핀/스크롤이 크게 어긋나지 않는다.

실패 예:

- 반복 위반이 너무 길게 나열되어 우선순위를 알 수 없다.
- 대표 요소가 실제 문제와 관계없는 항목을 가리킨다.
- 값은 보이지만 어떤 수정이 필요한지 알 수 없다.

### S12. 토큰 기준 소스가 바뀌거나 없을 때 이해한다

사용자 목표: 검사 기준 토큰이 무엇인지, 토큰 스냅샷 또는 브리지 상태가 결과에 어떤 영향을 주는지 이해한다.

검증할 사용자 도움: 사용자가 검사 기준의 신뢰도를 판단하고, 결과를 과신하거나 잘못된 기준으로 수정하지 않아야 한다.

검수 페이지: fixture, 실제 업무 페이지

절차:

1. 토큰 스냅샷이 있는 상태에서 검사한다.
2. 가능하면 브리지 연결 상태에서 검사한다.
3. 토큰 스냅샷이 없거나 로딩 실패한 상태를 확인한다.
4. 같은 페이지에서 결과 변화가 사용자에게 설명되는지 확인한다.

통과 기준:

- 토큰 기준이 없으면 사용자가 검사 신뢰도를 과대평가하지 않는다.
- 브리지/스냅샷 상태 문구는 사용자 행동을 방해하지 않는다.
- 토큰 기준 변화 후 재검사가 가능하다.
- 결과 목록은 토큰 수와 위반 수를 혼동하게 만들지 않는다.

실패 예:

- 토큰 수가 위반 개수처럼 보인다.
- 기준 토큰이 없는 상태에서도 정상 기준 검수처럼 보인다.
- 기준 변경 후 이전 결과가 stale 상태로 남는다.

## 결함 분류 기준

### P0. 검사 신뢰도 손상

- 위반을 놓치거나 잘못된 카테고리로 표시한다.
- 클릭한 결과가 다른 요소를 가리킨다.
- 일부 검사인데 전체 검사처럼 보인다.
- 오류 상태에서 정상 결과처럼 보인다.
- 사용자 가치 손상: 사용자가 잘못된 수정 결정을 내리거나, 릴리즈 가능한 품질이라고 오판한다.

### P1. 사용자 작업 차단

- 목록에서 인스펙터 카드 버튼을 클릭할 수 없다.
- 패널이 화면 밖으로 나가 조작할 수 없다.
- 큰 숫자나 긴 텍스트가 레이아웃을 깨뜨린다.
- 대형 DOM에서 브라우저가 멈춘다.
- 사용자 가치 손상: 사용자가 위반을 발견해도 위치 확인, 복사, 수정 요청 같은 다음 행동으로 넘어가지 못한다.

### P2. 이해도 저하

- 토큰 수와 위반 수가 혼동된다.
- `N곳`, `N개`, `N건` 표현이 무엇을 세는지 불명확하다.
- 빈 결과와 오류 결과가 구분되지 않는다.
- 잘린 텍스트의 전체 의미를 확인할 방법이 없다.
- 사용자 가치 손상: 사용자가 결과를 다시 해석하거나 동료에게 물어야 해서 검수 시간이 늘어난다.

### P3. polish/일관성

- hover/focus 시각 피드백이 약하다.
- 같은 정보의 용어가 화면마다 다르다.
- 간격, 정렬, 컬러 톤이 디자인 시스템 기대와 다르다.
- 사용자 가치 손상: 도구 자체가 디자인 시스템 검수 도구답지 않게 느껴져 신뢰가 낮아진다.

## 릴리즈 전 최종 통과 기준

- `npm test` 통과
- `npm run qa:uiux` 통과
- S01-S10 fixture 수동 검수 통과
- S02, S04, S05, S08, S11 실제 업무 페이지 검수 통과
- P0/P1 결함 0건
- P2 결함은 명확한 후속 이슈 또는 문서화된 제한 사항이 있어야 함
- 새 UI 수정이 있으면 `docs/verification/uiux-captures/`에 최소 1개 이상 증빙 캡처 추가
- 각 필수 시나리오에서 "사용자가 얻은 도움"이 한 문장으로 설명 가능해야 함

## 자동화 후보

- hover card 유지와 토큰 복사 성공 피드백
